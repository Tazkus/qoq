Minimal Summary

When an enterprise buyer submits a multi-line order, the backend validates account eligibility, reserves inventory per order line, charges the buyer once for the accepted subset, creates supplier payouts per accepted supplier, emits fulfillment tasks, and records every skipped or failed line for audit and customer support review.

Trigger POST /enterprise/orders with one buyer and one or more order lines
Result One order aggregate, zero or more fulfillment tasks, zero or more supplier settlement records
Default path Validate, reserve, charge accepted lines, settle suppliers, dispatch fulfillment

Backend Workflow Decomposition

Use an ordered list for the canonical countable steps, then add a flowchart when branches or loops make the shape hard to scan.

  1. Receive and normalize the order request.
  2. Validate buyer account, contract terms, and credit limit.
  3. Evaluate every order line for catalog status, supplier availability, inventory, and compliance restrictions.
  4. Reserve inventory for accepted lines and mark rejected lines with explicit reasons.
  5. Calculate buyer charge once from accepted lines plus fees and discounts.
  6. Authorize payment for the aggregate accepted amount.
  7. Create supplier settlement records grouped by supplier.
  8. Create fulfillment tasks for accepted lines and audit records for every rejected or failed line.

Branching and Exception Paths

Use a table when each branch needs an exact condition, behavior, result, and return rule.

Branch Condition Behavior Result Control flow
Default accepted order Buyer is eligible and at least one line passes all checks. Reserve accepted lines, charge accepted total, create settlements and fulfillment tasks. Order status becomes PARTIALLY_ACCEPTED or ACCEPTED. Continues through settlement and fulfillment.
Early termination buyer invalid Account suspended, contract expired, or credit limit unavailable. No line evaluation, no inventory reservation, no payment authorization. Order status becomes REJECTED. Terminates before inventory checks.
Partial acceptance line rejected Some lines fail catalog, inventory, supplier, or compliance checks. Rejected lines are excluded from payment and fulfillment but written to audit output. Accepted lines continue; rejected lines are visible to support. Returns to main path with accepted subset.
Retryable payment timeout Payment provider returns timeout before authorization state is known. Hold reservations, schedule reconciliation job, do not dispatch fulfillment yet. Order status becomes PAYMENT_PENDING_REVIEW. Pauses main path until reconciliation resolves.
Compensation payment declined Payment provider returns a definitive decline. Release all reservations and cancel supplier settlement drafts. Order status becomes PAYMENT_FAILED. Terminates after compensation.

Data and Collection Handling

Use a matrix for multiplicity. It is easier to audit than prose when item-level and aggregate-level rules both exist.

Dimension Rule Failure behavior Finalization impact
Input shape One buyer, one order header, one or more order lines. Empty line list rejects the whole order. No reservation, charge, or settlement occurs.
Iteration Line validation and inventory reservation run per line; payment runs once after aggregation. A failed line does not block other lines unless no accepted lines remain. Accepted subset continues to aggregate charge.
Filtering Inactive SKU, blocked supplier, restricted region, or insufficient inventory excludes a line. Excluded lines are reported with reason codes and written to audit records. Excluded lines are never charged or fulfilled.
Mapping Each accepted line maps to one fulfillment task and one supplier settlement allocation. Mapping failure for one accepted line marks that line as failed and releases its reservation. Remaining accepted lines may still finalize.
Aggregation Buyer charge aggregates accepted line totals, shipping fee, service fee, and contract discount. Invalid aggregate pricing blocks payment authorization. No fulfillment dispatch until aggregate payment is authorized.
Partial failure Partial line failure is allowed before payment; payment decline fails the accepted subset as a group. Reservations are released for group-level payment decline. Order may end as rejected, partially accepted, pending review, or accepted.
